# Priorify.app Product Operations

Use the Priorify.app MCP server at `https://priorify.app/mcp` as the source of truth. If the user has not identified a workspace or product, resolve the available scope before querying deeper records. Tool schemas stay authoritative. Follow the lifecycle below when the similarly named call would do the wrong thing.

For reviews and prioritization:

1. Read the relevant product context and open work before recommending changes.
2. Separate recorded facts from your recommendations.
3. Explain the small number of signals that determine the proposed order, such as urgency, impact, dependencies, risk, and blocked work.
4. Preserve stable Priorify.app identifiers in the result so the user can follow up precisely.

Match the record's lifecycle:

- Projects. A task belongs to at most one project, or to none. Read `get_project_schema` before writing a new planning record type. Charter writes use `put_project`, planning records use `put_project_record`, and a native task on its current project uses `put_project_task`. Move a task with `remove_project_link`, then link the destination with `put_project_record`. Restore an archived project before changing its tasks. A projects grant still requires separate task write access for task edits. Saved project updates are immutable server-captured snapshots.
- Tasks. `put_task` updates partially against the task's current `expected_version`; a `CONFLICT` returns the current task. Pass null to clear a nullable field. A waiting task records whom it waits on in `waiting_on` and the day an answer is expected in `waiting_until`. Both apply only while the status is waiting. Clear `waiting_on` with an empty string and `waiting_until` with null. Moving the task out of waiting clears both. A workspace may define its own board columns, such as Review or Blocked. Each column counts as one status. `list_task_columns` lists them, and `put_task` with a column's `board_column_id` moves a task there and sets its status to match. Changing only the status moves the task to the first column of that status. Owners and admins change the columns in the browser. `put_task` with `parent_task_id` makes a task a sub-task of another open task in the workspace, and null makes it top-level again; a task cannot sit under itself or one of its sub-tasks. `list_task_relations` returns a task's parent, its sub-tasks with done/total progress, and its links. `put_task_relation` adds `blocked_by`, `blocks`, `related`, or `duplicate_of`, and `remove_task_relation` removes one. Blocking cannot loop, a related pair is one link, and a duplicate has one original. Close a duplicate by linking it with `duplicate_of`, then setting its status to done with `put_task`. `reorder_tasks` sets the shared manual order people see on the board: pass one group of a product's tasks, top first. `list_tasks` returns each task's `manual_position`, and reordering never changes a task's version or History.
- Comments. `add_task_comment` writes Markdown. Pass `parent_comment_id` to reply to a top-level comment; threads are one level deep. Mention a person as `[@Name](#mention-user-<profile id>)` or an agent as `[@Name](#mention-agent-<agent id>)`. Mentioned people are notified, a mentioned agent finds it in its work inbox, and mentions of anyone who cannot open the task are ignored. Mention only someone who needs to act or know. `list_task_comments` returns `parent_comment_id`, `resolved_at`, and reaction counts. `resolve_task_comment_thread` folds a thread away or reopens it. `put_task_comment_reaction` adds or removes a reaction such as ✅ or 👀, a light way to acknowledge a comment without another message.
- Saved views. `list_task_views` returns the shared views and the person's own that apply to a product, each with its filters and layout. A filter value is "" for any, "a,b" for any of those, or "!a,b" for none of them. Use a view to understand what a team watches, then query with `list_tasks`. Saving, sharing, and starring views stay in the signed-in app.
- Creating records. Omit `record_id`, `product_id`, or `task_id` to create; the server assigns the id. Passing an id always means update and needs that record's `expected_version`.
- Knowledge. Collections belong to a workspace, product, or project, and reading or writing one needs a Knowledge grant that covers that scope. Private and restricted collections, including a person's My notes, stay hidden from `list_knowledge_collections` until that person grants this agent access. `request_knowledge_collection_access` returns a browser handoff and grants nothing. Find pages with `search_knowledge`. `search_knowledge_runbooks` finds Architecture runbooks without copying them. Create folders, pages, and files with `put_knowledge_item`. Read a page with `get_knowledge_item` before saving its structured body with `put_knowledge_page`. `move_knowledge_item` moves an item with its subtree. Each page save is a revision, so restore an earlier one with `restore_knowledge_version` instead of retyping it. `get_knowledge_file` and `export_knowledge_collection` return authenticated URLs. Fetch them with the same OAuth token. `put_knowledge_link` connects an item to another record and never grants access to it. `create_knowledge_task` creates a task pinned to a source revision, and any selected text becomes visible to the task's audience. Publishing a public snapshot needs the person's explicit public-sharing consent. Otherwise `request_knowledge_public_share` hands the decision to them.
- Budgets. `delete_budget_settings` removes one product's limits for one currency, such as a currency added by mistake. Pass the currency of an existing `get_budget_overview` settings row and that row's version as `expected_version`. Expenses, advertising spend, and link costs recorded in that currency stay.
- Search and store. Period comparisons, coverage, cohorts, and position bands are `get_seo_analysis`. Save that comparison as a task with `create_seo_investigation`. The same evidence returns the existing task. The investigation name and copied link stay in the browser. Import one completed Search Console property window with `trigger_integration_sync` and `history_range`. `get_store_metric_summary` returns daily totals summed across territories. Per-country figures are paged `store_metric` rows.
- Portfolio and links. `get_portfolio_product_summaries` returns rows for products this connection may read. `list_products` includes each product's completeness score. `compute_product_completeness` lists every configured check: `missing_checks` says what to create, and `satisfied_checks` names the records behind each passing check. The total follows the product's `completeness_config`. Do not retry a check marked `human_gated`, such as a logo that needs a real file; ask the person instead. Record weekly or monthly scorecards as a `timeline_event` with `event_type` `metrics_snapshot`, a period, and structured `metrics`, not in the product summary. Create a related-record link with `put_domain_record` and entity `record_link`. Remove that link with `remove_record_link` and leave both records in place. A link has no archive state and cannot be edited. Replace one by removing it and creating another.
- Files and credentials. File bytes never belong in a tool argument. Prepare the signed upload, upload the bytes to the returned URL, then finalize. That lifecycle covers task and comment attachments, identity images, assets, expense documents, and Knowledge files (`prepare_knowledge_upload`, then `finalize_knowledge_upload`). The first asset of a type becomes current; make a later one current with `set_current_asset`. Long-lived integration credentials and authenticated monitor setup stay in the signed-in browser. `create_integration_connection` only queues a setup request, needs integrations write for the product, and a workspace owner or admin finishes it in the browser. Start Ads OAuth from MCP, let the browser complete consent, then read status and finalize from MCP.
- Workflows. A draft can change. Publishing creates an immutable version plus durable run state. `decide_workflow_step` submits requested input or resumes a delay. Human-approval gates are visible over MCP, and only a person in the Priorify.app dashboard can decide them. A workflows grant still requires the task, routine, or agent-work permission a node uses.

Creating a workspace, billing, legal acceptance, accepting an invitation, transferring ownership, deleting a workspace, inviting an owner, saving or sharing a task view, assigning an agent, changing agent capacity or routing, and answering an intervention stay in the signed-in UI. `save_workspace` updates an existing workspace. `recommend_work_assignment` explains eligibility and leaves the work unassigned.

Do not change priority, status, assignment, budgets, publication state, permissions, or other records unless the user asks for that change. Before a consequential write, summarize the intended effect and use Priorify.app's preview, expected-version, idempotency, grant, and approval mechanisms whenever the matching tool exposes them. Never bypass a pending approval or infer permission from access to the tool.

Treat authentication separately from workspace authorization. A transport-level OAuth challenge may require connection or token refresh. An authenticated `connection_inactive` result means the user should review **Settings → Agent connections** in Priorify.app; repeatedly starting OAuth will not repair that workspace binding. If a documented tool or schema field is missing after a Priorify.app release, refresh the client's MCP session and start a new conversation when that client caches tools per session.

When data is incomplete or a tool is unavailable, state the missing evidence and give the most useful next query or user action instead of inventing state.
